# Graph Trajectories + JEV

This repository is an experiment in representing games as graphs, preserving how those graphs change over time, and using the resulting data to study decisions.

Disney Lorcana is the test environment. The larger idea is not specific to card games: it applies to any turn-based system with a finite set of legal actions and deterministic transitions once an action is chosen.

The project currently has two connected capabilities:

1. **Graph trajectories** generate structured records of complete simulated games.
2. **JEV** inspects one recorded state and evaluates the legal actions available from it.

The important distinction is that the trajectory pipeline records experience across time, while the current JEV integration reasons about one state at a time. Connecting those two into a learned, experience-based decision system is future work.

## The Short Version

```text
Lorcana decks
    |
    v
Graph-based rules engine
    |
    v
Random game rollout
    |
    v
Episode: every state connected through time
    |                              |
    v                              v
Per-card trajectories         State + legal actions
and narratives                    |
                                   v
                              JEV evaluation
```

The rules engine answers **what can happen**. The episode records **what did happen**. The trajectory tools describe **what each card experienced**. JEV evaluates **what looks strategically sound now**.

## Why Graphs?

A game state is naturally relational:

- the game points to the current player and current turn step;
- players have lore, ink, hands, boards, and discard piles;
- cards have identity, stats, status, and zone;
- edges encode relationships, abilities, and currently legal actions.

Legal actions are represented directly in the graph as edges such as `can_ink`, `can_play`, `can_quest`, `can_challenge`, and `can_pass`. Executing one of those edges creates the next state.

The supported transition is deterministic: given the same state and selected action, the engine produces the same next state. Game generation is still random because decks are shuffled and the simulator chooses among available actions.

## From States to Episodes

A single state is only a snapshot. To preserve time, a completed game is exported as an **episode**.

```text
output/episodes/<id>.episode/
|-- graph.dot
|-- history.txt
|-- result.json
|-- deck1.dek
`-- deck2.dek
```

`graph.dot` contains every state in the game. Each node is namespaced by its state index, and the same entity is connected between adjacent states with a `next` edge.

```text
p1.mulan.a@0  ->  p1.mulan.a@1  ->  p1.mulan.a@2
     hand              play             exerted
```

This rotates the data from a sequence of boards into a bundle of entity histories:

```text
Board view:       state 0 -> state 1 -> state 2 -> state 3

Trajectory view: Mulan  0 --------> 1 --------> 2 --------> 3
                 Simba  0 --------> 1 --------> 2 --------> 3
                 Stitch 0 --------> 1 --------> 2 --------> 3
```

Both views contain the same game. They answer different questions.

- Board view: "What was true at this moment?"
- Trajectory view: "What happened to this entity over time?"

## Trajectories and Narratives

The trajectory extractor turns an episode into JSONL records for the game and for each card that appeared. A card record includes its zone, exerted state, damage, available outgoing action types, and its inferred role in the transition.

```bash
just build-trajectories output/episodes/<id>.episode
```

The narrative builder converts those records into deterministic, human-readable card stories grouped across episodes.

```bash
just build-narratives
just build-narratives output/episodes/<id>.episode
```

These narratives are generated by code and templates. They are not JEV output and are not produced by a trained language model.

## What JEV Adds

[JEV](https://docs.typesafe.ai/api) is TypeSafe's System One model. This repository uses the `jev-latest` model to evaluate structured game state with typed questions.

JEV does not generate another move and ask the engine whether it was legal. The engine first computes the legal action set, then JEV evaluates only those candidates. This separates responsibilities:

- **Rules engine:** legality and state transitions
- **JEV:** strategic evaluation
- **Human or future agent:** whether to execute the recommendation

JEV currently uses two response primitives:

- **Noul:** a probability-like yes/no judgment for whether one action is strategically sound
- **Choice:** a distribution and selection across several candidate actions or action classes

The integration never applies the selected action to the game. It is an analysis surface, not an autonomous player.

## The JEV Request Flow

```text
Episode graph
    |
    v
Extract state N
    |
    +--> board state
    |      - turn and phase
    |      - lore and ink
    |      - hand and board
    |      - discard and deck counts
    |      - card stats and text
    |
    `--> legal action edges
           - end
           - ink
           - play
           - quest
           - challenge
                |
                v
        Human-readable candidates
                |
                v
       TypeSafe System One API
                |
                v
     Scores, rankings, confidence
```

The browser talks only to the local Flask server. The server reloads the authoritative episode state, rebuilds its legal actions, sends the request to TypeSafe, and maps the returned choice back to the engine action description. The API key remains on the server.

## Default Recommendation

The default "What should I do?" analysis evaluates a state at three levels:

1. **Per action:** Is each legal action strategically reasonable?
2. **Within each class:** If several cards can be inked, played, quested, or used to challenge, which option is strongest?
3. **Across classes:** Is the strongest direction to ink, play, quest, challenge, or end the turn?

This layered structure avoids forcing every question into one large flat choice. It can show that several actions are reasonable while still ranking the best option within a category and the best category overall.

## Context Lenses

The board supports optional free-form context:

- player tendencies;
- deck strategy;
- relevant past matches;
- future lines under consideration.

The default analysis can repeat the same questions through separate **lenses**, including player, deck, history, future, and selected combinations. Comparing those outputs shows how sensitive a recommendation is to additional context.

This is context-conditioned evaluation, not trajectory learning. Past matches and future lines are currently entered as text; they are not retrieved automatically from generated episodes.

## Free-Form Questions

The UI also supports up to ten custom questions in one request. Each question can be restricted to selected action classes.

Examples:

- "What is the safest play if I expect a challenge next turn?"
- "Which card should I ink?"
- "How can I maximize lore pressure this turn?"

The server validates the request, filters the engine-generated legal actions, sends all questions in one upstream call, and returns the selected label, engine description, probability distribution, and confidence.

## Running the Project

### 1. Install dependencies

```bash
just setup
```

### 2. Generate games

```bash
# Two shuffle seeds, three games per seed
just generate-games 2 3
```

Generated episodes are written to `output/episodes/`.

### 3. Configure JEV

Set the TypeSafe API key in the environment:

```bash
export TYPESAFE_API_KEY="..."
```

Or add it to a local `.env` file:

```text
TYPESAFE_API_KEY=...
```

`.env` is ignored by the repository.

### 4. Start the state browser

```bash
just serve
```

Open <http://127.0.0.1:8765>, choose an episode, and select a state.

The server provides:

- a visual board for the current player;
- navigation across turns and state transitions;
- the engine-generated legal actions;
- the default layered recommendation;
- context-lens comparisons;
- free-form JEV questions.

### 5. Run tests

```bash
just test
```

## Offline JEV Tools

The live server extracts states directly from episodes. The same data can be materialized for debugging.

```bash
python bin/build-jev-request.py output/episodes/<id>.episode <state-index>
```

This writes:

```text
jev/<id>/<state-index>/
|-- state.json
`-- criteria.json
```

`state.json` is the structured world state. `criteria.json` maps engine action descriptions to human-readable labels.

A Choice request can then be printed without calling the API:

```bash
python bin/build-jev-choice.py \
  jev/<id>/<state-index> \
  "What should I do?"
```

Add `--ask` to send it to JEV:

```bash
python bin/build-jev-choice.py --ask \
  jev/<id>/<state-index> \
  "What should I do?"
```

## What Exists Today

- A graph-based Lorcana state model
- Legal-action computation for pass, ink, play, quest, and challenge
- Support for a limited set of keywords and mechanics
- Random game simulation
- Deterministic transitions and replayable action paths
- Complete episode export with temporal `next` edges
- Per-card trajectory extraction
- Deterministic trajectory narratives
- A browser for inspecting episode states
- JEV evaluation constrained to engine-generated legal actions
- Layered default recommendations and optional context lenses

## What Does Not Exist Yet

- A complete Lorcana rules engine
- Exhaustive search or Monte Carlo Tree Search
- A trained graph neural network
- Automatic retrieval of similar historical episodes
- Vectorization or nearest-neighbor indexing of trajectories
- A policy that executes JEV's recommendation
- Evidence that JEV improves win rate over the random baseline
- A feedback loop that learns from JEV choices and game outcomes

## How This Relates to the Trajectory Thesis

The original trajectory idea argues that a current state is not always enough: useful decision evidence can live in how entities arrived there, what happened after similar actions, and which historical paths led to good outcomes.

The repository has implemented the data foundation for that idea:

```text
simulation -> episodes -> temporal graph -> entity trajectories
```

The JEV work has implemented a separate decision surface:

```text
current state + legal actions + optional text context -> typed evaluation
```

They are adjacent, but they are not yet one learning system. JEV does not currently consume extracted trajectories, compare the state with prior episodes, or derive confidence from experience density.

The natural next integration is:

```text
current state
    + legal actions
    + retrieved similar states
    + relevant card trajectories
    + observed outcomes
        |
        v
      JEV
        |
        v
contextual, evidence-backed action evaluation
```

That would preserve the engine as the authority on legality, use episodes as reusable experience, and use JEV to synthesize structured evidence without claiming optimal play.

## Current Boundaries

This is a research prototype, not a complete Lorcana agent.

- "Legal action" means legal according to the mechanics currently implemented by this engine.
- JEV evaluates snapshots; it does not yet learn from generated trajectories.
- Random rollout data reflects the simulator's action policy and can be biased.
- Confidence returned by JEV is model confidence, not statistical confidence from historical coverage.
- Optional player, deck, history, and future context is sent to the external TypeSafe API.
- The local server is intended for local development and should not be exposed as a production service.

The project is best understood as an inspectable pipeline for moving from deterministic graph simulation to temporal data and, now, to constrained model-assisted decision analysis.
